# 微信登录用户昵称记录设计

2026-11-03。用户明确推翻可选昵称方案，要求直接切分支实施；本说明按该指令修订。实现方选择下面的必填交互，不再要求额外审批。

同日追加：登录页顺序调整为先微信身份验证、复用已有昵称，缺昵称才补填；原设计的先填昵称再登录由 [追加设计](2026-11-03-ledger-profile-editing-design.md) 替代。后端缺昵称禁止业务访问的约束不变。

## 目标和边界

在 `t_users` 增加昵称，方便部署者识别使用者。登录页必须填写/选择昵称后进入账本；已有会话缺昵称的用户也必须补填。微信 code 仍由服务端校验，昵称是用户提供的展示资料，不能保证等于其微信当前昵称，不能用于身份或权限判断。历史用户昵称不能从 openid 反查。

## 数据与接口

- 显式 `007_user_nickname.sql` 为 `t_users` 增加 `nickname VARCHAR(64) CHARACTER SET utf8mb4 NOT NULL DEFAULT ''`，中文注释，迁移可重试并保留历史记录。
- `POST /api/v1/auth/wechat` 接收可选 `nickname`。提供时去首尾空白，要求 1–64 个 Unicode 码点，拒绝控制字符和非法 UTF-8。code 校验成功后，在创建会话的同一事务保存昵称。省略昵称兼容旧客户端，但缺昵称账号只能使用身份查询、补填、退出接口；业务请求返回 403 `nickname_required`。省略昵称不清空已有值，显式空白返回 400。
- `PATCH /api/v1/auth/me` 只接收非空 `nickname`，使用当前会话身份更新，只更新自己的资料；未知字段拒绝。
- 登录及 `GET /api/v1/auth/me` 返回 `id`、`nickname`，会话读取查询最新昵称。内存与 MySQL 实现一致。不返回 openid、session_key。

## 客户端

登录页采用 `form bindsubmit` + 原生 `input type="nickname" name="nickname"`，直接读取提交值，避免微信昵称选择/输入失焦时序漏值。新登录必须提交昵称；有效会话缺昵称时显示补填表单，调用 PATCH 后进入账本。会话已有昵称直接进入。401 正常回登录；403 `nickname_required` 回登录补填且保留令牌。设置页显示昵称并允许修改，保存后刷新会话中的资料；错误保留输入并提示重试。

不新增头像、手机号或管理后台。昵称变更不自动跟随微信同步。业务数据与现有账本权限不改变。

测试覆盖中文/emoji、新用户、重复登录、旧会话补填、更新后全部会话读取、空白与过长、伪造身份字段、未认证更新、未填写昵称业务拦截。隔离 MySQL 测试覆盖旧数据、重复迁移、DDL 成功但版本未写入的恢复。

运行 Go race 全套测试（含隔离 MySQL）、vet、构建、Node 全套测试与页面检查。开发者工具编译、真实微信与真机验证分别记录。本次在功能分支修改代码，不部署；真实数据库迁移前必须备份。
