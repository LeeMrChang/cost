# 账单账户标签与搜索能力回归

2026-11-04。来源：业务评审。用户确认两件事：① 记账时可选账户标签并让明细展示账户，直接在功能分支实施；② "搜索备注/分类名"按方案 B 处理。执行方式为当前会话 TDD 实施，不新增审批关卡。

## 背景

- 本项目"账户"是用户自建的记账标签（现金/微信/支付宝/银行卡/其他），不绑定银行卡、不读取任何外部账户数据。`t_accounts`、`/api/v1/accounts` 与账单 `account_id` 字段及余额聚合（期初 + 收支 + 转入 − 转出）均已存在。
- 现状缺口：记账页从不传 `account_id`，所有账单落库为未指定账户，账户余额恒等于期初值；明细列表也不显示账户。
- 搜索复核结论：后端 MySQL 查询（`LOCATE(BINARY ?,BINARY note)>0 OR category_id IN (SELECT id FROM t_categories WHERE ... LOCATE(...,BINARY name)>0)`）与内存存储均已实现"备注或分类名"匹配，此前的评审判断有误。本次不改查询，只补回归测试锁定行为。

## 设计

- 记账页新增账户选择条，置于分类宫格与金额卡之间，横向滚动 chip：首项"不指定账户"（`account_id=0`），其后为启用账户，图标沿用账户页的类型映射。
- 默认选择：优先记忆的上次账户（storage `cost_last_account`，须在可见账户中存在），否则"不指定账户"。保存成功后更新记忆，编辑场景不覆盖为历史值之外的行为。
- 编辑账单：回填 `pendingEdit.account_id`；原账户已停用时仍显示并标记"（已停用）"，沿用 `utils/ledger.allowed()` 的处理。
- 保存时 POST/PATCH 均携带 `account_id`；PATCH 传 0 表示清除账户（后端 `NULLIF(?,0)` 语义，用户显式选择"不指定账户"即清除）。
- 账本、搜索、日历三处明细行在 `account_id` 非零时显示账户名；未指定账户不显示，避免噪音。`utils/ledger.groups()` 已支持 `accountName`，调用方补拉 `/api/v1/accounts` 并传入。
- 后端零代码变更；新增 HTTP 回归测试覆盖按备注搜索与按分类名搜索两条路径（内存存储）。部署到线上后需确认运行版本包含该查询逻辑。

## 非目标

- 不做账户余额调整、退款、报销/不计收支开关（后续批次）。
- 不改 `/api/v1` 接口契约，无数据库迁移。
- 不做多账本、多用户共享。
