# 小程序审核整改：游客可体验 + 延迟登录

## 背景与证据

2026-11-14 微信审核驳回，原文：

> 小程序打开一进入【首页】页面，未浏览体验功能服务，即要求授权手机号码、头像、昵称进行授权登录，请在用户体验浏览功能服务后，再自行选择授权登录。

代码证据（本次实测）：

- `miniprogram/app.json` 的 `pages[0]` 是 `pages/login/index`，冷启动即登录页。
- `pages/login/index.js` 的 `onShow`/`signIn` 只在 `user.nickname` 存在时 `enter()`，昵称是进入门槛。
- `utils/api.js` 的 `request()` 在无会话时 `clearSession()` + `goLogin()`，任何页面一调接口就被弹回登录页。
- `backend/internal/api/api.go` 对除 profile 路由外的请求返回 403 `nickname_required`，客户端同样 `goLogin()`。

结论：入口强制登录、昵称强制补齐，两处都违反「先体验、后授权」。

## 目标

1. 冷启动不触发任何微信授权，首页可浏览、可试用记账。
2. 登录只在用户主动点击（或需要云端能力）时发生。
3. 昵称、头像不再是进入门槛。
4. 游客期间的记账数据安全保留，登录后合并进账本，重复提交不重复入账。

## 非目标

- 不引入多账本、多用户、共享账本。
- 不改金额（整数分）、时区（Asia/Shanghai）、预算模型。
- 不做离线同步冲突合并以外的复杂策略：游客数据只增不合并同一条记录。
- 不改后端认证、数据库结构、App ID 或部署。

## 行为

### A. 入口与游客浏览

- `app.json` 的 `pages` 顺序改为账本页在前，登录页保留但不再是启动页；`tabBar` 不变。
- 未登录（游客态）时的页面行为：
  - **账本**：读取本地游客记录渲染，顶部一条可点击的提示「游客模式 · 点此登录同步」；预算卡隐藏；头像隐藏。
  - **记账**：可正常记账，写入本地；分类使用内置游客分类表；隐藏账户选择条（account_id 固定 0）。
  - **统计**：本地计算当月收支/结余与分类排行，图表按现有组件渲染；范围切换仅支持月。
  - **搜索 / 日历**：只检索本地游客记录。
  - **设置**：显示登录入口与「游客数据说明」，不调用需要登录的接口。
  - **分类管理 / 账户 / 预算 / 账本资料**：引导登录，不直接报错。
- 登录入口固定在账本页顶部提示与设置页。

### B. 登录与昵称

- 登录页保留，供主动进入；未填昵称也可登录，客户端提交默认昵称「微信用户」，之后可在设置页修改。
- `utils/api.js`：
  - 新增 `isAuthenticated()`。
  - `request()` 的自动跳转登录改为显式选项：默认不再 `goLogin()`，401 只清会话并抛出可识别错误，由页面决定展示「登录后继续」。
  - 403 `nickname_required` 同样不再自动跳转。
- 登录成功后若存在游客数据，触发合并（见 C）。

### C. 游客数据与合并

- 存储键：`cost_guest_entries`（数组），仅存本机，不上传。
- 游客记录字段：`local_id`（本地自增，用于编辑/删除）、`category_key`、`kind`、`amount_cent`、`occurred_at`、`note`、`client_request_id`（`guest-` + 时间戳 + 随机）。
- 合并时机：登录成功、账本页 `onShow` 检测到已登录且存在游客记录。
- 合并方式：逐条 `POST /api/v1/entries`，携带原 `client_request_id`；成功即从本地移除。
- 部分失败：保留失败项，提示「N 条未同步，下次进入账本会重试」；不阻塞界面。
- 幂等：依赖后端按 `client_request_id` 去重，重复提交不会重复入账。
- 分类映射：游客分类用固定 `key`，合并时按名称匹配服务端分类；无匹配回退到同 `kind` 的第一个可用分类，并计入「已归入默认分类」提示。
- 账户：游客记录一律 `account_id: 0`（未指定）。

### D. 游客分类表

- 新增 `miniprogram/utils/guest-categories.js`：与后端 `DefaultCategories` 同名的 24 项（支出 12、收入 12），`id` 使用 101–124 本地段位，合并时按名称匹配。
- 仅游客态使用；服务端分类加载成功后以服务端为准。

## 数据与接口

- 不新增后端接口、不改数据库。
- 复用 `POST /api/v1/entries` 的 `client_request_id` 幂等。
- 客户端新增：`api.isAuthenticated()`、`request(..., { redirectOnAuth })` 选项、`utils/guest-store.js`（读写/合并）。

## 权限与安全

- 游客数据只存 `wx.storage`，不同步、不上传、不含身份信息。
- 登录仍走微信 code 换会话，后端认证不变。
- 单人单账本约束不变；游客合并只写自己的账本。

## 验收标准

1. 清除缓存后冷启动直接进入账本页，全程无授权弹窗、无跳转。
2. 游客态可完成一次记账，列表与统计立即反映；杀进程重进后仍在。
3. 游客态可编辑、删除自己的本地记录。
4. 登录后本地记录被合并进服务端账本，本地清空；连续两次登录不产生重复记录。
5. 不填昵称也能登录并进入，昵称显示为「微信用户」，设置页可修改。
6. 未登录点「预算/账户/分类管理」得到登录引导，不是错误提示或强制跳转。
7. `node --test miniprogram/tests/*.test.js`、`node miniprogram/tests/validate.js` 通过；新增测试覆盖 1–6。
8. 微信开发者工具手动验收（需用户执行），真机与正式版另行记录。

## 风险与回退

- **审核仍可能不认可**：若审核员认为核心功能仍必须登录，可在体验版备注里说明「游客可完整体验记账，登录仅用于云端保存」。
- **分类名称漂移**：后端改名会导致映射回退到默认分类；提示里说明，不静默。
- **本地数据丢失**：清缓存/卸载会丢游客数据，设置页需写明。
- **范围回退**：若 B 部分工作量超预期，可先只上线 A（入口与授权整改），B 单独排期；A 已能满足本次驳回意见。

## 决定（已确认并实现）

1. 默认昵称「微信用户」，设置页可改。
2. 游客态「统计」只做月范围，切换周/年/自定义时提示登录。
3. 合并失败提示「N 条未同步，下次进入账本重试」；分类排行只统计支出，与服务端一致。
